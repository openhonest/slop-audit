# L1.21 Orphan-code ratio (candidate)

**Status: candidate. Not scored, not in the twenty-indicator panel, not counted toward the slop-signal total.** A brand-new measured indicator needs its own pre-registration and must not be folded into a frozen indicator. The registration stub is `program-b-llm-correctness/Orphan-code ratio (registration).md` in the registrations tree. Until that is filed and the bands are calibrated, L1.21 is reported as an unscored observation beside the panel or not at all.

## 1. What it measures

The fraction of production code that no declared entry point can reach.

A symbol is **orphaned** when there is no path to it, in the reference graph of the current tree, from any member of the declared entry-point set, with test code excluded from the graph.

## 2. Why L1.12 does not already measure this

L1.12 is the unreachable-code ratio, and its operational definition delegates to reference counters: `vulture`, `ts-prune`, `knip`, `staticcheck`, the Rust and Ruby dead-code lints. Every one of them answers "does anything reference this symbol." A test references it. So a module with no production caller and a full test file reads as live to all of them.

This is a necessary-condition check treated as sufficient. Having no references is necessary for being orphaned; it is not sufficient, because a symbol can be referenced and still be reachable from nothing that runs in production. The error is therefore one-sided: L1.12 can only be wrong in the passing direction, and it is wrong exactly on the population this indicator exists to find.

The circularity is what makes the case severe rather than merely missed. The test exists *because* the module exists, so the evidence of life is manufactured by the subject. Adding tests to dead code makes it look more alive, and because the orphan's covered lines count toward coverage, deleting it can lower the repo's coverage number. The measurement rewards keeping the defect.

L1.12 is calibrated and frozen and is not changed by this document. The two are reported side by side. They overlap without either containing the other: L1.12 also catches unused locals and unreachable branches that a symbol-level reachability walk does not, and L1.21 catches the tested orphan that L1.12 cannot see.

## 3. Entry points are declared, never inferred

The entry-point set is supplied by the adopter, in a file in the repository. The analyzer does not guess it.

This is not deference; it is the same decidability argument the finite-testability definition makes in its §6. Dynamic dispatch, reflection, name-based lookup and runtime registration make "what can call what" undecidable in the general case. Inference is therefore unsound in the direction that matters, and an unsound guess here does not produce a wrong number, it produces a deletion. The declaration is what makes the question computable, and it is the bound the measurement states about itself.

Declaration is also the only thing that separates an orphan from a library's public surface. In a published library the exported API has no internal caller by design, and its tests genuinely are the only in-repo callers. Without a declared set, any tool must either delete the API or bless the corpses. With one, both cases are trivial.

Admissible entry points:

- process entry points (`__main__`, a `main` function, a console-script or binary target declared in packaging metadata)
- request handlers registered with a server, and the router or app object that registers them
- scheduled jobs, cron targets, queue and message consumers
- the exported public API of a library, named as a surface rather than symbol by symbol
- plugin and hook targets declared in packaging metadata (for example a `pytest11` or equivalent entry point)
- anything else the adopter declares, with a reason recorded beside it

An undeclared entry point is a defect in the declaration, and the indicator will report its subtree as orphaned. That is the intended pressure: the declaration is a claim about what the system is for, and it is worth making explicit.

## 4. Tests are excluded from the graph

Test files are not entry points and their references do not confer reachability. This is the whole point of the indicator, and it is the one rule that must not be softened for convenience.

A test that exercises a symbol reachable from a declared entry point is ordinary. A test that is the only thing referencing a symbol is evidence of an orphan, not evidence against one.

## 5. Fail-close direction

When a call target cannot be resolved statically, the target is treated as **reached**.

This is the opposite direction from the finite-testability meter, which fail-closes to UNRESOLVED and counts it against the code, and the asymmetry is deliberate. There, an unprovable claim is an unattested one and the conservative act is to withhold the green. Here, the consequence of being wrong is that someone deletes live code, so the conservative act is to assume life. The two rules share one principle: fail toward the outcome whose cost you can survive.

The price of that choice is that the number is a lower bound. A repo whose dispatch is mostly dynamic will report few orphans, and that is not a clean bill of health, it is an unmeasurable one.

## 6. Mandatory coverage disclosure

Because the number is a lower bound, the indicator MUST publish its own resolvable fraction beside the ratio: what share of call and reference sites the walk resolved, against what share it could not and therefore treated as reaching everything.

The disclosure is decomposable, never a bare scalar. A scalar lies by aggregation, and the dangerous hole here is a module that is both unresolvable and large. Report it per module, and report the unresolved sites by construct (reflective access, runtime registration, string-named dispatch) so the reader can see which of them a repository relies on.

A low resolvable fraction is itself a true finding: the code is too dynamic to measure, and the score is a floor.

## 7. The measure

```
L1.21 = orphaned production LOC / total production LOC
```

Reported with the orphaned symbol count and the resolvable fraction, since LOC alone hides whether the orphans are one large corpse or a hundred small ones.

Production LOC excludes test trees, generated files, and vendored dependencies, on the same exclusions L1.12 uses, so the two ratios share a denominator and can be read against each other.

**Bands are not set.** They are the subject of the pre-registration and must be derived, not asserted. Reporting L1.21 with invented bands would repeat the calibration debt the panel already carries.

## 8. The output is a decision, not a delete list

The finding is: *nothing reaches this from any declared entry point.* The two honest resolutions are to declare it as an entry point or to delete it, and both are cheap. The dangerous state is the third one, where nobody has decided and the tests quietly vote to keep.

Forcing the decision is the tool's job. Making it is not.

## 9. The indicator must be shown to fail

L1.21 is a gate, and a gate whose failing arm has never executed is not a gate. The implementation carries a paired test that plants a module reachable from no declared entry point, in a repository whose other measurements are clean, and requires the indicator to name it. A check that has only ever been observed passing is unverified in exactly the way an unexercised branch is.

The same obligation applies to the exclusion rules: a test that plants an orphan *with* a full test file, and requires it to still be named, is the one that proves the L1.12 blindness is actually closed.

## 10. Relationship to the AI-provenance hypothesis

The motivating hypothesis is that orphan-code fraction is higher, and grows faster per unit of change, in codebases generated and maintained by AI agents. The proposed mechanisms are that deletion requires whole-program confidence a bounded context cannot supply, that abandoned attempts are stranded by session statelessness, that agents test per module rather than per path and so camouflage what they strand, and that some constructs are born unreachable rather than falling out of use.

**None of that is part of this indicator's definition.** L1.21 measures orphan fraction in any codebase, of any provenance, and is meaningful without the hypothesis being true. The hypothesis is a separate empirical claim, it is confounded by repository age and churn rate, and it requires its own registration and its own provenance measurement before any result is reportable. Keeping the two apart is what allows the indicator to be used by people who do not accept the hypothesis.
