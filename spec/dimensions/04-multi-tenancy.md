### 4.4 Multi-tenancy

**Lifecycle category.** Data architecture.

**Definition.** Multi-tenancy is the application's mechanism for keeping the data of one customer (tenant) isolated from the data of every other customer in a shared database, shared application, or shared infrastructure context. A mature multi-tenancy system enforces tenant boundaries at a **non-bypassable enforcement layer**, meaning a layer the developer cannot accidentally skip when writing a new query or a new code path. The enforcement layer can live in several architecturally valid locations: the ORM itself (global query filters, scoped repositories), framework middleware that intercepts database calls before they reach the database (FastAPI dependency injection that wraps the ORM, Django middleware that injects query scopes, Spring AOP that intercepts repository methods, SQLAlchemy event listeners that mutate every query), the database itself (PostgreSQL row-level security policies, multi-schema isolation), or a dedicated tenant-isolation service that brokers all data access. The criterion is not the location; the criterion is that a developer writing a new query has to actively bypass the enforcement layer to produce a cross-tenant query, and the bypass leaves a visible signature in code review. The opposite is the application that "remembers" to filter by tenant in some queries and forgets in others, which produces cross-tenant data leakage as a routine bug.

**Industry threshold.** Tenant context enforced at a non-bypassable layer (ORM, framework middleware, database row-level security, or equivalent); no code path that returns data from a tenant other than the current one without an explicit, code-reviewable bypass; support for dedicated instances for high-value or security-conscious customers. Drawn from JISEM 2025 ("Multi-Tenant System Design for Platform Scalability"), which documents 99.97% cross-tenant isolation success in properly isolated systems, and from SailPoint's Multi-Tenancy Research Series (2025) on isolation patterns at scale.

#### Layer 2 form (mechanical / artifact-based)

**Layer 2 inspection procedure.**

1. **Determine whether the application is multi-tenant at all.** If the application serves only one tenant by deployment (one customer per running instance), this dimension scores *Not Applicable*. Most enterprise SaaS applications are multi-tenant; most internal tools at a single organization are single-tenant. Confirm with the client which model applies before proceeding.
2. **Locate the tenant identifier.** Find the field, column, or context variable that represents the current tenant. Common names: `tenant_id`, `organization_id`, `company_id`, `account_id`, `workspace_id`. Inspect how it is populated on each request.
3. **Identify the non-bypassable enforcement layer.** Determine where in the architecture tenant filtering is automatically applied. Inspect each of the following candidate locations in order until you find one (or confirm none exists): the ORM layer (global query filters), framework middleware that wraps the data access path (FastAPI dependency injection, Django middleware, Spring AOP), ORM event listeners (SQLAlchemy `before_execute`, Hibernate filters), database-level enforcement (PostgreSQL row-level security, multi-schema isolation), or a dedicated tenant-isolation service.
4. **Search for unscoped queries.** Use `grep` to find queries on tenant-scoped tables that do not go through the enforcement layer. Look especially for raw SQL execution (`session.execute(text(...))`, `db.query(...)`, `cursor.execute(...)`) on tables that should be tenant-scoped. A single unscoped query is sufficient for the Layer 2 form to score *Partial* at best.
5. **Test the boundary directly (the disqualifier check).** If a test environment is available, attempt a manual cross-tenant access (authenticated as tenant A, request a resource that belongs to tenant B by guessing or enumerating IDs). The application should return 404 or 403, not the resource. **This is the most reliable single test in the entire dimension.** If cross-tenant access succeeds, the dimension scores *Absent* without further inspection regardless of any other findings.

#### Layer 3 form (qualitative specified judgment)

**Layer 3 inspection procedure.** Four markers, each scored present / partial / absent.

**Marker 1: The non-bypassable enforcement layer is genuinely non-bypassable.** Test it: write a small example query that tries to escape the enforcement layer using the same patterns as the existing code (raw SQL, direct ORM call without the standard wrapper, etc.). If the example fails to execute (the enforcement layer catches it), the layer is real. If the example executes and returns cross-tenant data, the layer is technically present but not load-bearing — it only works because developers happen to follow the convention. A bypass that requires an explicit `IgnoreQueryFilters()` call (or equivalent) AND is enforced by a linter or build-time analyzer is acceptable; a bypass that anyone can write by accident is not. Present = the enforcement layer cannot be silently bypassed; partial = it can be bypassed but the bypass is documented and code-reviewable; absent = bypass is silent and routine.

**Marker 2: Cache keys include tenant context.** Sample 5 cache key construction sites in the codebase. Verify each one includes the tenant identifier as part of the key (or that the cache instance itself is tenant-scoped, which is functionally equivalent). Cross-tenant cache leakage is the most common multi-tenancy bug after forgotten WHERE clauses and is the failure mode where the database-level enforcement is correct but the cache layer leaks anyway. Present = all 5 sampled cache sites include tenant context; partial = 3 or 4 do; absent = 0, 1, or 2 do.

**Marker 3: The audit trail records tenant context with every operation.** Inspect the audit log schema (which overlaps with dimension 4.5). Determine whether every audit record includes the tenant identifier as a structured field, not just embedded in a free-form description. Without this, post-incident forensics cannot identify which tenant's data was accessed during a breach, which is one of the most common failure modes in multi-tenant breach response. Present = tenant ID is a structured field on every audit record; partial = tenant ID is in some records but not others; absent = no tenant ID in audit records.

**Marker 4: The dedicated-instance deployment path is documented and tested.** Determine whether the architecture's claimed support for dedicated-instance deployment (one customer in their own database, one customer in their own Kubernetes namespace, etc.) is actually documented in operational runbooks AND has been exercised at least once with a real or test customer. A dedicated-instance path that exists only in architectural diagrams but has never been tried is a fiction. Present = documented runbook AND evidence of at least one successful dedicated deployment; partial = documented but never exercised; absent = not documented and not exercised.

**Layer 3 scoring rule for the dimension.** Score Layer 3 *Present* if 3 or 4 markers score Present. *Partial* if 2 markers score Present. *Absent* if 0 or 1 markers score Present. **However, if Marker 1 (genuine non-bypassability) scores Absent, the entire dimension scores at most *Partial* regardless of the other markers, because the enforcement layer is the foundation everything else depends on.**

#### Layer 4 questions (deferred to Phase 1)

- Is the multi-tenancy model the right model for this application's growth trajectory? (Pool-based multi-tenancy works at small scale but breaks at large scale; per-tenant deployment scales linearly but is operationally expensive.)
- Are there subtle cross-tenant leakage paths through shared infrastructure (logs, metrics, error reporting, third-party services) that would only show up in an experienced architect's review?
- Would the multi-tenancy model survive a sophisticated attacker who has access to one tenant and is trying to pivot to another?

**Combined scoring rubric.**

- ***Present.*** Layer 2 form passes (non-bypassable enforcement layer identified, no unscoped queries found, manual cross-tenant test returns 404/403) AND Layer 3 form scores Present (3 or 4 of 4 markers).
- ***Partial.*** Layer 2 form passes but Layer 3 has gaps (2 markers Present); OR Layer 2 is Partial (enforcement exists but has gaps, some unscoped queries found) but Layer 3 scores Present; OR Marker 1 of Layer 3 scores Absent (enforcement is technically present but bypassable).
- ***Absent.*** Layer 2 form fails (manual cross-tenant test succeeds, OR no enforcement layer, OR multiple unscoped queries on tenant-scoped tables); OR Layer 2 form passes but Layer 3 scores Absent.
- ***Not Applicable.*** The application is single-tenant by design (one customer per deployment). Document the reasoning.

**Common failure modes.**

- **The forgotten WHERE clause.** A query that filters by every relevant attribute except the tenant identifier, returning data across tenant boundaries. The most common multi-tenancy bug and the easiest to find with grep. The non-bypassable enforcement layer exists precisely to make this bug impossible to write.
- **Tenant in the URL but not in the query.** The application accepts a tenant identifier in the URL (`/api/tenant/123/users`) but the query handler ignores it and returns all users. Sometimes the URL tenant is validated against the user's session and then discarded, with the query running unscoped.
- **Raw SQL escape hatch.** The ORM correctly applies tenant filters to all queries that go through the ORM, but the codebase has scattered `session.execute(text("SELECT * FROM invoices WHERE..."))` calls that bypass the ORM entirely. The enforcement layer is technically present but routinely bypassed.
- **The "admin override" backdoor.** A code path (often labeled debug or admin) that explicitly disables tenant filtering. Common as `IgnoreQueryFilters()` calls in EF Core, `unscoped` blocks in Rails, or a custom `with_all_tenants()` context manager. Often legitimately used by support staff and forgotten about, then discovered by an attacker who compromises a support account.
- **The shared cache key.** The application correctly scopes its database queries by tenant but caches results under keys that do not include the tenant identifier, so tenant A sees tenant B's cached response. (This is the same failure as 4.8 cache key omits tenant; the two dimensions overlap here.)
- **Cross-tenant ID enumeration.** Resources are accessible by guessing sequential integer IDs across tenants, with no per-resource tenant check. Requesting `GET /api/invoices/12345` returns the invoice regardless of which tenant the requesting user belongs to.
- **The "global config" that contains tenant data.** A configuration table or environment variable system used to store tenant-specific settings, with no isolation between tenants.
- **No dedicated-instance path.** The architecture cannot deploy a single tenant to its own database even when a high-value customer requests it, requiring the team to either lose the customer or rebuild the architecture.
- **Enforcement at the application layer only.** Tenant filtering is applied as a habit by developers in every controller / service method, but there is no enforcement layer that catches the case where someone forgets. This is *Partial*, not *Present*, even if every current query happens to be correct.

**Note on two Presence examples.** Multi-tenancy is the one dimension in Section 4 that provides two Presence examples instead of one. The reason is that two structurally different enforcement layers (ORM-layer query filters versus middleware-layer statement rewriting) are both equally valid Present states for this dimension, and showing only one risks training the assessor to recognize only that one as Present. Assessors should treat either pattern as Present; what matters is that the enforcement layer exists, is non-bypassable, and catches the query-that-forgot-to-scope failure mode. The single Absence example below is in a third language and framework, as usual.

**Example presence (C# / ASP.NET Core, ORM-layer enforcement).** An ASP.NET Core SaaS application using Entity Framework Core with global query filters. The `DbContext` has `modelBuilder.Entity<Invoice>().HasQueryFilter(i => i.TenantId == _currentTenant.Id)` configured for every tenant-scoped entity. The `_currentTenant` is injected via DI from a `TenantResolver` middleware that extracts the tenant from the JWT claim and validates it against the user's allowed tenants. Every query through the DbContext is automatically scoped to the current tenant; there is no syntactic way for a developer to write a cross-tenant query without explicitly bypassing the filter via `IgnoreQueryFilters()`, which is forbidden by a custom Roslyn analyzer that fails the build. Raw SQL execution via `dbContext.Database.ExecuteSqlRaw()` is wrapped by a custom extension method that injects the tenant predicate before execution. Dedicated database deployment is supported via a per-tenant connection string resolved at startup.

**Example presence (Python / FastAPI, middleware-layer enforcement).** A FastAPI application using SQLAlchemy with a `tenant_scoped_session` dependency that returns a session pre-configured with a `before_execute` event listener. The listener inspects every SELECT, UPDATE, and DELETE statement, identifies tenant-scoped tables by name, and rewrites the WHERE clause to add `tenant_id = :current_tenant_id` before the statement reaches the database. The current tenant ID is set on the session via a contextvar populated by an authentication middleware that runs before the dependency is resolved. Every route handler receives the tenant-scoped session via `Depends(get_tenant_scoped_db)` and there is no syntactic path to obtain a non-tenant-scoped session without invoking a separately-named `Depends(get_admin_db_with_audit)` dependency that logs every use to a structured audit table. Raw SQL execution is gated by the same listener; an attempt to bypass it raises an exception. Dedicated-instance deployment is supported via per-tenant database URLs resolved by the auth middleware at request time.

**Example absence (Ruby / Rails).** A Rails SaaS application where tenant filtering is the developer's responsibility on every query. Most controllers use `current_user.organization.invoices.where(...)` which scopes correctly, but the assessor finds three places where developers wrote `Invoice.where(...)` directly because they forgot the scope. One of those queries is in an admin dashboard accessible to any authenticated user. There is no `default_scope`, no `before_action` filter that wraps queries, no Rack middleware that intercepts ActiveRecord, and no row-level security in the Postgres database. The codebase has no tenant column on the `audit_logs` table at all (audit logs are global), and no test in the test suite verifies cross-tenant isolation. There is no dedicated-instance deployment path; every customer is on the same Postgres database with the same connection pool.

**Time budget.** Approximately 90 to 105 minutes for an experienced assessor on a multi-tenant codebase: 30 to 45 minutes for the Layer 2 inspection (the manual cross-tenant test takes 5 minutes and can short-circuit the entire dimension), 60 minutes for the Layer 3 marker assessment. Less if the application is single-tenant by design.
